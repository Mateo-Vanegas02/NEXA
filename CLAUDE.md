# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Proyecto
NEXA: web app de mototaxis (pasajeros, conductores, admin) en Spring Boot 3.4.4 / Java 21 con MongoDB y frontend Thymeleaf + JS vanilla. El código, los nombres de paquetes y las clases están en español; mantén esa convención. Los commits siguen Conventional Commits (`feat:`, `fix:`, `docs:`, `style:`, `refactor:`).

## Comandos
```bash
./mvnw spring-boot:run                    # dev en http://localhost:8080
./mvnw clean install                      # build + tests (lo mismo que corre CI)
./mvnw test                               # todos los tests
./mvnw -Dtest=ServicioServiceImplTest test            # una clase
./mvnw -Dtest=ServicioServiceImplTest#metodo test     # un método
./mvnw clean package -DskipTests          # JAR en target/MotvirsWeb-0.0.1-SNAPSHOT.jar
docker compose up --build                 # perfil prod, lee .env
node --test src/test/js/*.test.mjs        # pruebas JS (mapa, solicitudes, extra voluntario, filtros de campos; sin npm)
```
No hay linter configurado ni build de frontend (sin npm/bundler). `.mvn/` no está versionado: si `./mvnw` falla, usa un `mvn` instalado. Los tests `@SpringBootTest` (contexto completo) llevan `@Tag("requiere-mongo")`, se omiten por defecto y necesitan una MongoDB real (`MONGODB_URI`, p. ej. un `mongod` local) para correrlos con `-Dexcluded.groups=none`; los unitarios no la necesitan.

## Arquitectura
Arquitectura por capas (detalle y reglas de dependencia en `docs/ARQUITECTURA.md`). Paquete raíz `com.example.MotvirsWeb`: `presentacion/` (`web`, `api`, `dto`) → `aplicacion/` (`servicio`, `herramientas`, `verificacion`, `util`) → `dominio/` (`modelo`, `regla`, `repositorio`); `infraestructura/` (`seguridad`, `config`, `correo`, `socket`, `verificacion`) implementa lo técnico. `aplicacion/puerto` define las interfaces (`NotificadorCorreo`, `NotificadorTiempoReal`, `EmisorTokens`) que implementa infraestructura: los servicios dependen de ellas, no de las clases concretas. Las dependencias solo apuntan hacia el dominio.

- **Dos superficies HTTP en la misma app:** controladores `Controller*`/`AuthController*` sirven vistas Thymeleaf con sesión + form login (`/auth/login`, procesado en `/login`); `Api*Controller` exponen `/api/**` autenticado con JWT vía `infraestructura/seguridad/JwtAuthFilter` (`JwtService`). CSRF se ignora solo para WebSocket, `/api/auth/login`, peticiones con Bearer, `/auth/**` y `/public/**`: un POST/PUT/DELETE a `/api/**` desde el navegador con sesión debe enviar `X-CSRF-TOKEN` (de `input[name="_csrf"]`) o responde 403 "Forbidden".
- **Autorización centralizada:** todos los patrones de URL y su rol están en `infraestructura/seguridad/SecurityConstants.java` y se aplican en orden en `SecurityConfig`; las reglas por rol van antes de la regla general `/api/**`. Una ruta nueva debe registrarse ahí. Roles: `PASAJERO`, `CONDUCTOR` (requiere aprobación de admin), `ADMIN`.
- **Herencia de usuarios en MongoDB:** `Usuario` (abstracta) y sus subclases `Pasajero`, `Conductor`, `Admin` comparten la colección `Usuarios`, distinguidas por `@TypeAlias`. `Servicio` (colección `servicios`) embebe copias de pasajero/conductor (`PasajeroEmbedded`, `ConductorEmbedded`) y coordenadas, en vez de referencias.
- **Registro de conductor y documentos:** `POST /auth/registro/conductor` es multipart: número + foto (JPG/PNG/WebP; `registro-conductor.js` la reduce en el navegador a ~500 KB, el servidor admite máx. 5 MB) de licencia, tarjeta de propiedad, SOAT y tecnomecánica. `RegistroConductorService` crea conductor (PENDIENTE), su primer vehículo activo y los documentos, y deshace todo si algo falla; `DocumentosConductorService` valida el tipo real por contenido y guarda vía el puerto `AlmacenDocumentos` (GridFS en `infraestructura/almacenamiento`) con el número declarado en `documentos_conductor`. El admin las ve en `GET /api/admin/verificacion/documentos?email=` y `/documentos/{id}/archivo`. La ficha de revisión del admin es `static/js/verificacion-conductor.js` (funciones puras probadas en `src/test/js/verificacion-conductor.test.mjs`); los conductores antiguos, sin vehículo ni fotos, se muestran con "Sin foto" y un aviso.
- **Perfil y foto:** `GET|PUT /api/perfil` (nombre y teléfono; correo y licencia no se editan), `PUT|DELETE /api/perfil/foto` (multipart `foto`, JPG/PNG/WebP máx. 5 MB, validada por contenido) y `GET /api/usuarios/{id}/foto` (cualquier usuario autenticado). `PerfilService` guarda la foto vía el puerto `AlmacenDocumentos` (campos `fotoPerfilId/Tipo` en `Usuario`); `ConductorEmbedded`/`PasajeroEmbedded` llevan `fotoUrl`. UI: fragmento `templates/fragments/perfil.html` + `static/js/perfil.js` + `static/css/perfil.css` (el navegador encuadra en círculo y reduce a 512 px antes de subir).
- **Solicitudes del conductor:** `static/js/solicitudes-conductor.js` (lista "Cerca de ti" + pines de precio; funciones puras probadas en `src/test/js/solicitudes-conductor.test.mjs`). Aceptar es atómico (`ServicioRepository.tomarSiDisponible`, update condicional): el segundo conductor recibe 409. Al tomarse o cancelarse una solicitud se publica `{id, estado:'RETIRADO', motivo}` en `/topic/servicios-disponibles` (`NotificadorTiempoReal.notificarSolicitudRetirada`). El conductor no vigila el mapa: cada solicitud nueva emerge como tarjeta tipo Uber (máx. 3 a la vez, 45 s visibles; solo si no está en un viaje, sin modal abierto y con "Notificaciones" activas). Cada tarjeta muestra "Ganas $X" = (1 − comisión del conductor) × tarifa bruta (+ extra voluntario, cuando exista), el $/km y etiquetas ("+$ extra", "Lleva N min esperando", "Buen pago", "Cerca de ti"); la comisión real la entrega el servidor en `data-comision` de `#solicitudes` (`NivelesService.comisionDe`). "Ahora no" no la oculta: sigue en el mapa y baja al final de la lista (`ordenarConVistas`); lo "visto" vive en `sessionStorage` (por navegador, no por cuenta) y no vuelve a emerger.
- **Ubicación del pasajero y punto de recogida:** la posición sale del GPS (`watchPosition`, alta precisión; nunca se escribe) y se ve como punto con círculo de precisión. El punto de recogida arranca ahí y el pasajero lo mueve con un pin arrastrable o tocando el mapa: máx. 300 m de él (`nexa.recogida.radio-max-metros`, regla `PuntoRecogida`; `solicitar-viaje` envía `ubicacionPasajero` y responde 400 si está lejos) y pegado a la calle con OSRM `/nearest`. Reglas puras en `static/js/ubicacion-pasajero.js` (`src/test/js/ubicacion-pasajero.test.mjs`): geocodifica al moverse ≥ 50 m, recotiza si el punto se aleja > 150 m del cotizado (no mientras busca conductor), avisa con precisión > 150 m y exige una posición de menos de 2 min. Sin permiso de ubicación no se puede pedir viaje.
- **Deuda por cancelación = se cobra con el siguiente viaje:** no bloquea. La cotización trae `deudaPendiente`/`totalAPagar`; el pasajero acepta el total antes de pedir (`aceptaDeuda`, si no 402). Al finalizar `DeudaService.cobrarEnViaje` la descuenta (update condicional) y el conductor solo ve "Cobra al pasajero" (`DesgloseConductorDto.cobrarAlPasajero`), sin desglose; su comisión es sobre la tarifa. Saldo del conductor con NEXA: `SaldoConductorService` (`GET /conductor/saldo`, `/api/admin/conductores/saldos`; UI `saldo-conductor.js` y `saldos-conductores.js`). Correos en `NotificadorCorreo`: deuda registrada, condonada y aviso 15 días antes de bajar de nivel. Detalle en `docs/niveles/DECISIONES.md`.
- **Qué ve cada rol de un viaje (privacidad):** todo `Servicio` que sale hacia un navegador (REST y STOMP) pasa por `aplicacion/servicio/VisibilidadServicio` (`paraConductor` / `paraPasajero`, copia; la entidad no se toca). Cada uno ve solo la calificación y el comentario que él puso, nunca los del otro (ni el promedio mezclado). El conductor no ve comisión (ni monto ni tarifa bruta: `DesgloseConductorDto` solo lleva espera, extra, ganancia y `cobrarAlPasajero`), ni la deuda del pasajero: en su vista `tarifa` ya incluye la deuda cobrada con el viaje y los campos `deuda*` van en 0/null. `SaldoConductorService.VistaConductor` es lo que ve el conductor de su saldo (sin comisión ni deudas); el admin sigue viendo `SaldoConductor` completo. Todo endpoint o mensaje nuevo con un `Servicio` debe pasar por `VisibilidadServicio`.
- **Seguimiento del pasajero hasta la recogida:** con el viaje en `ACEPTADO` el pasajero reporta su posición (`POST /pasajero/ubicacion/{servicioId}` y `/api/pasajero/...`, `{latitud, longitud}`; 403 si no es suyo, 409 si ya no está aceptado) y el conductor asignado la consulta cada 4 s (`GET /conductor/pasajero-ubicacion/{servicioId}`, 204 si no hay una reciente). `SeguimientoPasajeroService` la guarda solo en memoria (vence a los `nexa.seguimiento.vigencia-segundos`=30 s, se borra al iniciar o cancelar) y no cambia el punto de recogida del servicio: el pin queda fijo, el conductor ve al pasajero como un punto aparte y la distancia a la recogida. Cliente: `ubicacion-pasajero.js` (`debeReportarSeguimiento`: mín. 3 s, ≥ 10 m o latido de 10 s) y `viaje-conductor.js` (`textoSeguimiento`), con un mini mapa en el modal del viaje. Tras recargar el pasajero retoma el viaje con `GET /pasajero/viaje-en-camino`. Con un viaje pedido el pin de recogida del pasajero ya no sigue a su GPS.
- **Viaje en vivo (real, sin simulación en el servidor):** con el viaje `ACEPTADO` o `EN_CURSO`, la posición que el conductor ya reporta con `POST /conductor/ubicacion` (y `/api/conductor/ubicacion`) la reenvía `ViajeEnVivoService` al pasajero por STOMP en `/topic/pasajero/{id}/posicion` (`NotificadorTiempoReal.notificarPosicionConductor`; payload `PosicionViaje`: fase, lat/lng, `distanciaRestanteKm`, `etaMinutos`; máx. 1 envío/s; `WebSocketAuthInterceptor` solo deja al pasajero dueño). Todo en memoria: sin consultas a Mongo por reporte. Con el viaje en curso se acumula el recorrido real (`ReglaViaje.debeGuardarPunto`, puntos ≥ `nexa.viaje.punto-minimo-metros`, tope `max-puntos-recorrido`) y al finalizar se guarda `Servicio.recorrido` y `distanciaRecorridaKm` (la vista `VisibilidadServicio` no los entrega al navegador). Reglas: `iniciar-servicio` exige `fechaLlegada` ("llegué" verificado, 409 si no) y `finalizar-servicio` lo puede hacer el conductor en cualquier tramo (el pasajero nunca finaliza): si su última posición vigente está a ≤ `nexa.viaje.radio-destino-metros` (150 m) del destino se cobra completo; si no, `ReglaViaje.factorCobro` cobra según lo recorrido (recorrido real < `nexa.viaje.umbral-cobro-completo`=50 % de la distancia cotizada → `fraccion-cobro-anticipado`=la mitad; desde la mitad, completo; sin datos para medir, completo). Se guardan `finalizadoAntesDelDestino` y `fraccionCobrada`, y `NivelesService.desgloseDefinitivo` factura `distanciaKM × fracción`. El pasajero ve la advertencia en el panel del viaje. "Llegué" exige estar a ≤ `nexa.llegada.radio-metros` (50 m) de la recogida y el cliente envía la posición que ya sigue (`ViajeActivo.posicion()`). `nexa.viaje.exigir-destino=false` solo en el perfil `dev` para el recorrido simulado (siempre cuenta como en el destino). `GET /conductor/viaje-activo` (y `/api/...`, 204 si no hay) devuelve el viaje ACEPTADO/EN_CURSO y retoma el seguimiento tras recargar o reiniciar el servidor. El panel del conductor ya no finaliza solo: botón "Finalizar viaje" (provisional hasta el rediseño).
- **Pantallas del viaje en curso (diseño Figma "Flujo del viaje"):** pasajero y conductor ven un panel flotante sobre el mapa por fase (A_RECOGER → EN_EL_PUNTO → EN_VIAJE; `ViajeFases.fase` la deduce de `estado` + `fechaLlegada`). Módulos en `static/js`: `viaje-fases.js` (lógica pura y textos, probada en `src/test/js/viaje-fases.test.mjs`), `viaje-panel.js` (DOM del panel; esqueleto fijo, solo actualiza textos, sin `innerHTML`), `viaje-mapa.js` (Leaflet: pines, moto con rumbo, ruta hecha/pendiente), `viaje-pasajero.js` (usado por `Dashboard_P_v2.js`: panel + `/topic/pasajero/{id}/posicion`; el formulario de solicitud se oculta con `.ride-request-container--viaje`) y `viaje-activo.js` (conductor: GPS real con `watchPosition`, reporta a `POST /conductor/ubicacion` cada ≥3 s/≥10 m/latido 8 s con `disponible:false`; esa respuesta trae `PosicionViaje` (200) o 204 sin viaje, de ahí salen ETA y distancia, nunca se calculan en el navegador; «Llegué» y «Finalizar» se habilitan por cercanía solo como ayuda visual, el servidor valida; retoma con `GET /conductor/viaje-activo`). Estilos en `static/css/viaje-panel.css` (hoja inferior en ≤720 px). La simulación del recorrido (`ruta-animada.js`) ya no se carga. Para el pasajero, `ConductorEmbedded` guarda `nivel`, `calificacion`, `vehiculo` y `placa` al aceptar (`ServicioServiceImpl.completarFichaConductor`, nunca impide aceptar) y `GET /pasajero/viaje-en-camino` devuelve además `servicio` (vista del pasajero) y `espera` (reglas de `nexa.espera.*` solo para el cronómetro). Pendiente sin backend: llamar/mensaje, compartir viaje y SOS.
- **Rutas reales (`ProveedorRutas`):** `ProveedorRutasConfigurado` elige por `nexa.rutas.proveedor` entre `recta` y `osrm` (por defecto desde que se activó) (`RutaOsrm`: distancia, duración y trazado polyline de `nexa.rutas.osrm-url`, timeout `osrm-timeout-ms`, caché 10 min, cae a línea recta si falla). **Cambiar a `osrm` cambia el precio** (calles reales en vez de recta × 1,3). La cotización guarda `Servicio.rutaGeometria` y `duracionEstimadaMin`. El servidor público de OSRM es una demo: en producción, uno propio.
- **Pasajero con solicitud pendiente:** una sola solicitud `SOLICITADO` por pasajero (`solicitarViaje` → 409 si ya hay otra). Mientras espera conductor, o con un viaje `ACEPTADO`/`EN_CURSO` (pasajero y conductor), no se puede cerrar sesión: `BloqueoCierreSesionFilter` (antes de `LogoutFilter`) responde con redirect al panel del rol con `?cierreBloqueado=true|viaje` (409 JSON si `Accept: application/json`); el panel lo avisa antes y ofrece "Cancelar solicitud" (que retira la tarjeta del mapa de los conductores). `GET /pasajero/solicitud-activa` (y `/api/pasajero/solicitud-activa`) permite retomarla tras recargar.
- **Extra voluntario (modelo v2.2, sección 12A):** mientras su solicitud espera conductor, el pasajero suma +$500/+$1.000/+$2.000 (tope $5.000 por viaje; `nexa.extra.*` en `modelo-nexa.properties`, regla pura `ModeloExtra`). `POST /pasajero/subir-oferta/{id}` (y `/api/pasajero/...`, body `{incremento}`) usa `ServicioRepository.subirExtra` (update condicional atómico: solo SOLICITADO, del pasajero, bajo el tope; 409 si cambió) y publica `{id, estado:'OFERTA_SUBIDA', extraVoluntario}` en `/topic/servicios-disponibles` (`NotificadorTiempoReal.notificarOfertaSubida`); la tarjeta del conductor vuelve a emerger. `Servicio` guarda `extraVoluntario` e `historialExtra`. Al finalizar, `NivelesService.conExtraVoluntario` suma E al total del pasajero y a la ganancia del conductor sin comisión, descuento ni XP; la tarifa T0 y el cargo de cancelación no lo incluyen. UI: `static/js/extra-voluntario.js` (funciones puras, `src/test/js/extra-voluntario.test.mjs`) y el modal `#extraModal` en el panel del pasajero; `GET /pasajero/solicitud-activa` devuelve tarifa, extra, margen y pasos.
- **Despacho por olas (`nexa.despacho.*`):** una solicitud se avisa primero a los conductores cercanos y el radio crece con el tiempo (0/25/50/75 s → 1,5/2,5/4/6 km; tope de 6 km, más lejos nunca llega; calibración en `docs/niveles/DECISIONES.md`). Con extra voluntario la solicitud va una ola por delante (`nexa.despacho.olas-por-extra`); en la última ola "Avisamos a N" suma a los conductores en línea sin posición vigente (retención de 10 min). Al aceptar se guardan `olaAceptacion` y `distanciaRecogidaKm`; `MetricasDespachoService` las resume en `GET /api/admin/despacho/metricas?dias=` (tarjeta del inicio del admin, `static/js/despacho-metricas.js`). La ola es función de `solicitadoEn` (regla pura `DespachoOlas`, sin estado). `DespachoService` filtra la lista de cada conductor (`ServicioServiceImpl.obtenerServiciosDisponibles`) y bloquea aceptar fuera de su ola (403). El conductor reporta su posición con `POST /conductor/ubicacion` y `/api/conductor/ubicacion` (`{latitud, longitud, disponible}`); `UbicacionConductorService` la guarda solo en memoria y vence a los 45 s. Sin posición vigente solo ve la última ola (opción B, pensada para la web, donde el navegador deja de reportar con la pantalla bloqueada). `solicitudes-conductor.js` reporta cada 5 s si se movió ≥ 30 m, con latido de 30 s (`debeReportar`), y recarga la lista cada 20 s. `DespachoScheduler` (cada 5 s) publica `{id, estado:'SOLICITADO', ola}` cuando una solicitud pasa de ola. `/topic/servicios-disponibles` ya no lleva la solicitud completa: solo `{id, estado}` y el cliente recarga la lista filtrada. El pasajero ve "Avisamos a N conductores" (`despacho` en `GET /pasajero/solicitud-activa`).
- **Tiempo real:** STOMP sobre WebSocket en `infraestructura/socket/WebSocketConfig` + `WebSocketService` (`/ws/**`, `/topic/**`) para seguimiento de viajes.
- **IA (Spring AI + Gemini 2.5 Flash):** `infraestructura/config/LlmConfig`; `ChatBotService` usa herramientas de `NexaTools` (chatbot de usuarios) y `AdminChatService` usa `AdminTools` (asistente del panel admin). Para dar nuevas capacidades al chatbot se añaden métodos tool en esas clases.
- **ML / optimización:** `SatisfaccionClienteService` carga el modelo Weka J48 desde `motvirs.model.path` (archivo `.model` en la raíz, se lee en runtime); `OptimizerService` usa OR-Tools.
- **Frontend:** NO hay SPA de React (se evaluó y se eliminó; sigue en el historial de git). Todo es Thymeleaf + JS plano. `templates/` (paneles en `pasajero/`, `conductor/`, `panel_admin.html`) con un JS y un CSS por vista en `static/js` y `static/css`. `static/js/ruta-animada.js` queda en el repo (con su prueba) pero ya no se carga: el viaje es real.

## Sistema de niveles
- **Modelo v2.3** (`docs/niveles/NEXA_Modelo_Tarifa_XP_Niveles_v2.3.docx` + sección 12A): reglas puras en `dominio/regla` (`ModeloTarifa`, `ModeloXp`, `PrioridadRecogida`, `CatalogoBeneficios`, `ModeloExtra`, `ZonaServicio`) con config única en `modelo-nexa.properties` (prefijo `nexa.`, `ModeloNexaProperties`); ningún número de negocio va en código. Decisiones: `docs/niveles/DECISIONES.md`.
- Pasajero: niveles desde 1 y sin techo (`X_n = 10·round(270(n−1)^1.5/10)`), descuento `min(1 % · nivel, 5 %)` desde el nivel 2, prioridad de recogida 15/25/35/45 s (niveles 2–5), favoritos desde el nivel 5, baja un nivel tras 90 días sin viajar (`xpTrasInactividad`). Conductor: nivel 1–5 por XP de 90 días (`400(n−1)²`) más requisitos de calidad; comisión 20/19/18/16/15 %. Se retiraron (también del código) tasa de servicio, Días NEXA, escudo, upgrade, cashback y Créditos NEXA. El J48 de satisfacción se reentrena solo con viajes v2.2 (mín. 30 calificados).
- Cotización y cobro: `CotizacionService` + `NivelesService.procesarFinalizacion` (comisión real al finalizar, llegada verificada, espera, cargo de cancelación, deuda del pasajero en `DeudaService`). Distancia por el puerto `ProveedorRutas` (hoy línea recta × 1,3).
- `NivelesService` orquesta las reglas y se invoca desde `ServicioServiceImpl` (finalizar → XP + desglose, calificar → ajuste de XP del conductor). XP idempotente: índice único `(viajeId, rol, motivo)` en `xp_eventos`. Jobs en `NivelesScheduler` (reproceso, inactividad, ventana 90 d).
- Migración única `infraestructura/config/NivelesMigracion` (marcador `niveles-v2.2` en la colección `migraciones`): los niveles guardados 0–4 pasan a 1–5 (`X_nuevo = X_{ℓ+1}`).
- API: `GET /api/niveles/me`, `GET /api/niveles/viajes/{id}/desglose`, `PUT|DELETE /api/niveles/favoritos/{id}`. UI: `static/js/niveles.js` + `static/css/niveles.css` (se activa con `data-nivel-rol` en `<body>`).

## Configuración y despliegue
- Los secretos van SOLO en variables de entorno, sin valor por defecto (`MONGODB_URI`, `JWT_SECRET`, `GEMINI_API_KEY`, `SPRING_MAIL_USERNAME`, `SPRING_MAIL_PASSWORD`; `APP_BASE_URL` obligatoria en prod; ver `.env.example` y `docs/SEGURIDAD.md`). `infraestructura/config/EntornoObligatorioPostProcessor` aborta el arranque si faltan. `application-dev.properties` (logging detallado) y `application-prod.properties` se activan con `SPRING_PROFILES_ACTIVE`. Los `@SpringBootTest` llevan `@Tag("requiere-mongo")` y se omiten por defecto (`-Dexcluded.groups=none` para correrlos).
- Este repositorio (`NEXA`) es la versión que se despliega en AWS; la producción actual sigue en Azure desde `NEXA_Origin` (`master`). Aquí no hay workflow de Azure. `.github/workflows/ci.yml` compila, prueba y construye la imagen Docker en cada push. GitHub Actions no debe depender de artefactos (cuota de 500 MB acumulados por mes en el plan gratuito): la imagen va a Amazon ECR, no a GHCR (los paquetes de GHCR comparten esa cuota).
- **Zona horaria única:** `MotvirsWebApplication.main` llama a `ZonaHorariaNegocio.aplicar()` antes de Spring y fija la zona por defecto de la JVM en `nexa.zona-horaria` (America/Bogota; se puede cambiar con `NEXA_ZONA_HORARIA`). Así `LocalDateTime.now()` y el reloj de niveles (`NivelesConfig`) coinciden; antes, en Docker/Azure (UTC), `solicitadoEn` quedaba 5 h atrás de las demás fechas del viaje y las métricas de despacho salían mal. Los viajes guardados antes del cambio conservan ese desfase en `solicitadoEn`.
- El servidor objetivo tiene 2 GB de RAM (heap 512m–1024m); evita cargar colecciones completas en memoria.
