# Decisiones tomadas (app móvil)

- La app solo cubre pasajero y conductor; el admin permanece en la web.
- Estado con Riverpod 3 (`Notifier`/`AsyncNotifier`); navegación con go_router y guards por rol (`core/router/app_router.dart`, función `redirigir`).
- Se usan repositorios mock por defecto (`USE_MOCKS=true`) porque el backend no soporta login de conductor ni registro JSON; con `USE_MOCKS=false` se usa la API real.
- No se usa `very_good_analysis` (exige documentar toda API pública y genera ruido); se usa `flutter_lints` + `strict-casts/inference/raw-types` + reglas extra.
- Sin refresh de token: el backend no lo ofrece; ante un 401 en ruta autenticada se cierra la sesión.
- El rol se obtiene del claim `roles` del JWT (el login solo devuelve `{token}`).
- Tiempo real por polling cada 5 s (el WebSocket del backend usa sesión web, no JWT). Solo corre con viaje activo, o en línea para el conductor.
- No hay endpoint de cotización: el estimado de tarifa es local (3000 + 1200/km, tasa 5 % entre 800 y 2500, Día NEXA −30 % con tope 3000). El total real lo calcula el backend.
- El destino se elige tocando el mapa (no hay geocodificación sin API key); el nombre es texto libre.
- "Rechazar" solicitud solo la oculta localmente (no existe endpoint).
- ~~Los Días NEXA se envían en español~~ (retirado en la Fase 5: Días NEXA ya no existe en el backend).
- Mapa: flutter_map + teselas de OpenStreetMap, sin API key. Centro por defecto: Cartagena (igual que la web).
- Tema oscuro forzado (identidad de la web); el tema claro existe pero no se activa por defecto.
- Subida de nivel: se compara con el último nivel guardado en `flutter_secure_storage` (`nivel_visto_<usuario>`) para mostrar la animación una sola vez.
- Textos en `lib/core/l10n/app_es.arb` (generación con `flutter gen-l10n`, salida versionada en `lib/core/l10n/gen`).
- Los archivos generados de freezed/json (`*.g.dart`, `*.freezed.dart`) se versionan para que el proyecto compile sin `build_runner`.
- Diseño tomado de las pantallas de Figma (`Descripcion_Pantallas_NEXA1.docx`): tema claro por defecto (azul de marca #0B5A82 + cian), con tema oscuro disponible; el mock server del documento se ignora.
- Landing pública `/inicio` (hero + servicios) antes del login; el onboarding de 3 pantallas solo aparece la primera vez.
- Navegación del pasajero: Inicio, Historial, Pedir viaje, Perfil. Niveles se abre desde la barra de nivel (`/p/niveles`); el conductor conserva la pestaña Niveles.
- "Pedir viaje": mapa + hoja deslizable. Destino por toque en el mapa; precio sugerido ajustable en pasos de $500 dentro de ±$1.000; ruta dibujada como línea recta (sin servicio de rutas sin API key).
- Calificación: las etiquetas (p. ej. "Puntual") se anteponen al comentario, porque `POST /calificar-servicio` solo recibe `calificacion` y `comentarios`.
- Seguimiento: la moto se coloca de forma aproximada según el estado (no hay GPS del conductor); llamar/mensaje usan `tel:`/`sms:` con el teléfono del conductor si existe; SOS llama al 123.
- El dashboard de admin (Machine Learning) de la maqueta queda en la web: la app es solo pasajero y conductor.
- Estructura por capas dentro de cada feature: `presentation/{controllers,screens,widgets}`; pantallas de viajes separadas en `pasajero/` y `conductor/`.
- Estilo oscuro de NEXA (fondo #020A12, cian) por defecto en toda la app; el logo es el icono oficial de la web (`static/icon/NEXA_ICO.ico` → `assets/images/nexa_logo.png`), sin iconos de moto como marca.
- `mostrarNexaPopup` (core/widgets): popup de marca siempre oscuro con logo, fondo difuminado y entrada animada (escala con rebote, fade, deslizamiento, halo pulsante y contenido escalonado); respeta "reducir animaciones". Se usa en bienvenida (tras login/registro), subida de nivel, SOS y cancelar viaje.
- Validación de formularios alineada con el backend (nombre, correo, teléfono 3XXXXXXXXX, contraseña ≥8 con mayúscula/minúscula/número); el servidor sigue siendo la autoridad. El mock exige la contraseña de las cuentas registradas y rechaza correos duplicados.
- `dart format` se corre sobre `lib test` (sobre `.` falla con rutas largas dentro de `build/` tras compilar Android en Windows).
- Origen y destino editables en "Pedir viaje": búsqueda de direcciones con Nominatim (OpenStreetMap, sin API key; debounce de 700 ms, mínimo 3 letras, resultados de Colombia priorizando cerca del origen) o toque en el mapa sobre el campo activo (con nombre por geocodificación inversa). Las consultas de texto se envían a nominatim.openstreetmap.org con un Dio propio (nunca con el token de NEXA). Para producción a gran escala conviene un proveedor propio (Nominatim self-hosted o similar), por la política de uso (1 petición/s).
- Splash: se muestra al menos 2,2 s (`splashMinimoProvider`) para que la marca se vea aunque la sesión se restaure al instante.
- Fase 2 (backend real): con `USE_MOCKS=false` el login acepta pasajeros y conductores aprobados; un conductor sin aprobar ve el estado y el motivo que devuelve el servidor (403 con `estadoValidacion`). El registro de pasajero llama a `/api/auth/registro/pasajero` y luego inicia sesión. El perfil (`GET|PUT /api/perfil`) muestra y edita nombre y teléfono; el correo no se edita. Estos endpoints existen solo en la rama `feat/api-movil-auth` del backend hasta integrarla a `master`.
- Registro de conductor (`/registro/conductor`): 13 campos más la foto de cada documento (licencia, tarjeta de propiedad, SOAT y tecnomecánica) con `image_picker` (cámara o galería, lado mayor ≤ 1600 px y calidad 85 para quedar bajo los 5 MB del servidor). Se envía como multipart a `POST /api/auth/registro/conductor`; no inicia sesión porque la cuenta queda PENDIENTE hasta que el administrador la apruebe. En el modo demo el mock deja la cuenta pendiente y el login la rechaza con ese aviso. Foto de perfil: `PUT|DELETE /api/perfil/foto` y `GET /api/usuarios/{id}/foto` (bytes con el token en la cabecera; no se usa `Image.network` para no filtrar el token en la URL). Cámara y galería van detrás de `SelectorImagen` para poder probar las pantallas sin el plugin; en iOS se añadieron los textos de permiso de cámara y fotos en `Info.plist`.
- Fase 3 (viaje del pasajero con el backend real): el precio lo fija el servidor. Al elegir destino la app llama a `POST /api/pasajero/cotizar` (valida la zona de Cartagena y usa la ruta por calles) y muestra tarifa, descuento por nivel, cargo pendiente y total; se retiraron el estimado local y el precio ajustable. `solicitar-viaje` ya no envía tarifa, distancia ni `upgrade`: envía `ubicacionPasajero` (GPS, el servidor exige la recogida a ≤ 300 m) y `aceptaDeuda`, que el pasajero debe marcar si hay cargo pendiente (sin eso el servidor responde 402). Seguimiento por polling cada 5 s: `GET /pasajero/servicios/{id}`, posición real del conductor con ETA y distancia del servidor (`GET /pasajero/posicion-conductor/{id}`, endpoint nuevo en la rama `feat/api-movil-auth`), y mientras el conductor va en camino la app reporta la posición del pasajero (`POST /pasajero/ubicacion/{id}`). Mientras se busca conductor se puede sumar un extra voluntario (+500, +1.000, +2.000; el tope lo pone el servidor). El desglose usa el modelo v2.3 (tarifa, descuento por nivel, recargo por espera, extra, cargo anterior). El WebSocket sigue sin usarse porque autentica por sesión web.
- Fase 4 (conductor con el backend real): en línea o con un viaje, cada 5 s la app reporta su posición (`POST /conductor/ubicacion`, `disponible:true/false`); sin eso el servidor solo le muestra las solicitudes de la última ola de despacho. Libre: pide `servicios-disponibles?lat&lng`; con viaje: refresca `viaje-activo` (204 = el pasajero canceló, se avisa), toma fase, distancia y ETA de la respuesta de `ubicacion` (nunca se calculan en el teléfono) y, yendo a recoger, la posición del pasajero (`pasajero-ubicacion`). Flujo por fases: «Llegué» (`POST /conductor/llegue/{id}`, el servidor exige ≤ 50 m de la recogida) → «Pasajero recogido» (`iniciar`, 409 sin llegada) → «Completar viaje» (`finalizar`); si el servidor reporta más de 150 m al destino se avisa antes de finalizar porque se cobrará según lo recorrido. Aceptar puede dar 409 (otro conductor la tomó) o 403 (fuera de su ola): se muestra el mensaje y la solicitud sale de la lista. Privacidad: el conductor solo ve un monto («Cobra al pasajero»); el desglose trae `cobrarAlPasajero` y su ganancia, sin comisión ni deuda, y el saldo con NEXA (`GET /conductor/saldo`) es la vista del conductor. La reconexión al abrir la app usa `viaje-activo`.
- Fase 5 (niveles del modelo v2.3): los niveles son números (sin nombres como Bronce o Plata). Pasajero: desde 1 y sin techo, descuento de `min(1 % · nivel, 5 %)` desde el nivel 2 y prioridad de recogida de 15/25/35/45 s (niveles 2–5). Conductor: niveles 1–5 y comisión de 20 % a 15 %. La app lee `GET /api/niveles/me` tal como viene (XP con decimales, `descuento`, `prioridadSegundos`) y muestra «Tus ventajas actuales» al pasajero. Se eliminaron Días NEXA, Créditos NEXA, tasa de servicio, escudo, cashback y upgrade del código, los textos y los tests; el mock sigue las mismas fórmulas del backend. Los textos «Nivel N» salen de `nombre`/`nombreSiguiente`, que ahora son el número.
- Fase 6 (entrega): `USE_MOCKS` ahora es `false` por defecto; la demostración sin backend es opcional (`--dart-define=USE_MOCKS=true`). La URL base es `API_BASE_URL` si se define; si no, `release` usa producción (HTTPS) y `debug` el backend local `http://10.0.2.2:8080` (el HTTP sin cifrar solo está permitido en `android/app/src/debug`). `tool/distribuir.ps1` compila por defecto contra producción. Los tests no dependen de esto porque sustituyen `useMocksProvider`.
- **Admin en la app (rama `feature/flutter-admin`, 9 nov. 2026):** la app suma el rol `admin` (`ROLE_ADMIN` en el JWT; en el mock, un correo que contenga "admin"), con rutas `/a/...` y barra flotante (Inicio, Satisfacción, Conductores, Perfil). Reemplaza la decisión de dejar el dashboard de ML en la web: la parte de redes neuronales es solo para la app. Inicio y Conductores quedan como "Próximamente" (siguen en la web).
- **Satisfacción con TensorFlow:** la app consume la Lambda `nexa-satisfaccion` según `docs/CONTRATO_SATISFACCION.md` (v0.1) con un Dio propio (`satisfaccionDioProvider`: misma sesión y manejo de 401, sin el prefijo `/api`). URL por `--dart-define=SATISFACCION_URL=...`; sin ella el panel avisa que no está configurado. El mock (`MockSatisfaccionRepository`) usa las cifras del diseño de Figma (`mKq1Yb7s7nBW9TmAf2O2wn`) y simula el avance de un entrenamiento.
- Los modelos de satisfacción son clases inmutables con `fromJson` escrito a mano (sin freezed), para no depender de `build_runner`.
- El entrenamiento se sigue con sondeo cada `Env.pollingInterval` solo mientras la pantalla "Entrenando" está abierta (provider `autoDispose`); al volver, el modelo muestra "Hay un entrenamiento en curso".
- Sin datos suficientes (300 calificaciones y 30 "no" por lado) se entrena en modo demo (datos sintéticos) y el panel lo indica; si nunca se ha publicado un modelo, se muestra el avance de los datos.
- Las gráficas (tendencia y tramos) se dibujan con widgets propios y `CustomPainter`, sin agregar dependencias.
- CI de la app: `.github/workflows/mobile.yml` (genera textos, revisa formato, `flutter analyze` y `flutter test`) en cada push a `feature/flutter-**` que toque `mobile/`.

- **11 nov. 2026 — la app consume el despliegue de AWS.** Este repositorio (`NEXA`, rama `app`) es la versión para AWS; la de Azure sigue en `NEXA_Origin`. Por defecto, debug y release usan la web de AWS (`Env.urlAws`, hoy `https://18-227-59-40.sslip.io` hasta tener dominio propio) y la Lambda `nexa-satisfaccion` (`Env.satisfaccionUrlAws`, URL pública que exige JWT de admin). `API_BASE_URL` y `SATISFACCION_URL` siguen sirviendo para cambiarlas (p. ej. backend local). `tool/distribuir.ps1` compila contra AWS. Al comprar el dominio solo cambia `urlAws`.
- **11 nov. 2026 — satisfacción solo con datos reales.** Se retira el modo demo: la app ya no pide entrenar con datos sintéticos (`entrenar()` sin parámetros, contrato v0.3) y «Entrenar ahora» queda deshabilitado mientras `datos.suficientes` sea `false`. `modo` es `real` o `sin_modelo`; sin modelo, el resumen y los factores dicen «Sin modelo todavía» en vez de «Modo demo». Reemplaza la decisión anterior de entrenar en demo sin datos. El entrenamiento corre en ECS Fargate (`ml/nexa_ml/entrenadora.py`); el generador de viajes falsos quedó solo en `ml/tests/`.
- **12 nov. 2026 — segundo plano, paso 1 (Android).** Plan «NEXA app: segundo plano, notificaciones y giroscopio», fase 3. Por ahora solo Android. El manifiesto declara ubicación en segundo plano (solo la pide el conductor, pantalla N03), servicio en primer plano de tipo ubicación (Android 14+), `WAKE_LOCK` y `POST_NOTIFICATIONS` (se pide en N01, nunca al abrir). `flutter_local_notifications` 22.3 (la 23 exige compileSdk 37) crea al arrancar los canales `nexa_solicitudes`, `nexa_viaje` y `nexa_cuenta`, con los mismos ids que el servidor (`docs/AVISOS_PUSH.md` en `main`); si falla, la app abre sin notificaciones. Se activa el desugaring de Java que pide el plugin. La CI compila además un APK debug para detectar errores de Gradle o del manifiesto; con Flutter 3.50 hubo que subir el Android Gradle Plugin a 9.1.1 (el mínimo que exige Flutter). Firebase (push) queda para el último paso de la fase.
- **12 nov. 2026 — segundo plano, paso 2: pantallas de permisos.** Cada permiso se pide con su pantalla y en su momento, nunca al abrir la app: N01 notificaciones (tras iniciar sesión, una vez), N02 ubicación «al usar» (el pasajero al entrar o al pedir viaje; el conductor al ponerse en línea), N03 segundo plano (solo conductor, la primera vez que se conecta; puede seguir sin él), N04 guía de batería por marca (Samsung, Xiaomi, Motorola, Huawei u otra) y E01 sin ubicación (abre los ajustes si se negó para siempre y se cierra sola al volver con el permiso). `ubicacionProvider` ya no pide permiso, solo lo consulta. Las reglas son puras (`ReglasPermisos`); lo «visto» se guarda en el almacenamiento seguro. Rutas `/permisos/*` (cualquier rol) y `/c/permisos/*` (conductor). Sin pedir viaje ni conectarse si no hay ubicación; sin plugin (pruebas) no se muestra nada y decide el servidor.
- **12 nov. 2026 — segundo plano, paso 3: el coordinador.** `CoordinadorSegundoPlano` (vigilado desde `NexaApp`) decide el modo con el estado que entrega el servidor, nunca por su cuenta: conductor en línea (GPS cada 15 s, precisión media), conductor con viaje (cada 3 s, alta), pasajero con el conductor en camino (cada 5 s, hasta que inicia el viaje) y apagado en todo lo demás. El GPS corre como servicio en primer plano de tipo ubicación (geolocator, notificación fija «En línea» / «Viaje en curso»), que mantiene viva la app con la pantalla apagada; el reporte al servidor lo siguen haciendo los controladores con su sondeo, ahora con la posición reciente del rastreador (`miPosicionProvider`). Con la pantalla apagada y sin viaje el conductor reporta cada 15 s en vez de 5. Android 14 no deja iniciar un servicio de ubicación desde segundo plano: con la app oculta solo se apaga y el cambio pendiente se aplica al volver. Sin permiso de ubicación no se prende. Límite conocido: si el usuario cierra la app desde recientes, Android termina el proceso y el servicio se detiene; si hace falta sobrevivir a eso, se evaluará `flutter_background_service`.
